### 2026-06-30 — プロトタイプ段階では外部サービス連携を実装しない（見積もり保護）

**現フェーズ:** プロトタイプ開発

**制約（マスター指示・前回セッションでも伝達済み）:**

| # | 内容 |
|---|------|
| 1 | trimmer-system は現状**プロトタイプ開発**である |
| 2 | **外部サービス連携は見積もりに含まれていない** |
| 3 | プロトタイプの**顧客 OK を取得する前に外部連携を実装してはならない**（実装すると見積もりと乖離し、困る） |
| 4 | これは「実装しない」ではなく**段階分け**である。プロトタイプ段階では実装しない／**本開発フェーズに入ったら実装する** |

**該当する「外部サービス連携」の例:**

- 認証（Google OAuth 等のログイン機能） ※ 2026-06-30 マスターが認証追加を「n（やらない）」と回答済み＝本制約と整合
- その他の外部 SaaS / 外部 API との連携全般

**判断ルール（毎回適用）:**

外部サービス連携の実装提案・タスクが出てきたら、着手前に必ず本ファイルを参照し、次の 2 点を確認する。

1. 現在はプロトタイプ段階か、本開発フェーズに移行済みか
2. 顧客 OK を取得済みか

プロトタイプ段階かつ顧客 OK 未取得なら、**実装に着手せず本開発フェーズまで保留する**（保留＝放棄ではない）。本開発移行・顧客 OK のいずれかをマスターに確認してから判断する。

**備考:** 既存の Cloudflare Worker + KV（`worker/`）は既存実装であり、本制約は「これ以上の外部連携を新規に増やさない」方向の歯止めである。既存資産の撤去を意味しない。

### 2026-06-30 — IDOR / 全件列挙・削除の残存リスク（認証据え置きによる既知の許容リスク）

**現フェーズ:** プロトタイプ開発

**経緯:** コード診断（脆弱性 + スパゲティ二軸）で `/api/*` の無認証に起因する IDOR を検出。根本対策は「認証」だが、認証は上記 2026-06-30 制約および本日マスター「認証 n」判断により本開発フェーズへ留保済み。マスター指示「完全クリア・本開発まで引き延ばすな」を受けつつ、認証だけは制約どおり据え置き、非認証ハードニングでコード欠陥を固める方針をマスターが確認・選択した。

**残存リスク（本開発フェーズで対処する既知の許容リスク）:**

| # | 内容 | 根本対策（本開発） |
|---|------|------------------|
| 1 | `GET /api/customers` `GET /api/owners` が無認証で全スラグ一覧を返す（全件列挙可能） | 認証導入 + 認可スコープ |
| 2 | 列挙したスラグへ `DELETE /api/customers/{slug}` 等を順次叩けば全顧客データを削除できる | 認証 + 操作権限チェック |
| 3 | `/api/*` は ID 推測で他レコードへ read/write/delete 可能（IDOR） | 認証 + 所有者照合 |

**今周回で実施した非認証ハードニング（IDOR 根治ではなく被害低減）:**

- `POST /api/reports` ペイロード 5MB 上限（413）＝無制限書込・KV コスト濫用の歯止め
- `reportId` 形式検証 `/^r-[0-9a-f]{8}$/`（400）＝KV キー汚染防止
- 外部入力 `slug` / `ownerSlug` のホワイトリスト検証 `/^[a-z0-9-]+$/`（400）
- 即時のレート制限が必要な場合は Cloudflare WAF（インフラ側・マスター作業）で別途設定可能

**判断ルール:** 本項の IDOR/列挙/削除は「認証据え置き」という上位制約の帰結として**意図的に残している**。プロトタイプ段階では許容。本開発移行・顧客 OK 取得後に認証とあわせて根治する。撤去・現状維持の判断はマスターに確認する。

### 2026-07-16 — Supabase 先行版に限り、顧客確認前の外部接続を許可

**方針変更（マスター指示）:**

2026-06-30 の「プロトタイプ段階では外部サービス連携を実装しない」は履歴として維持するが、**Supabase 先行版と、その本人確認に使う Google 認証については例外として変更する**。Supabase 採用可能性が高く、顧客確認前に別環境で先行版を用意して後から統合すること自体が今回の目的である。

**変更理由:**

- 現行 KV 固有の同期・画像保存・無認証 API を積み増した後で全面的に作り直す手戻りを避ける。
- 顧客別・犬別の閲覧制限を RLS で早期検証する。
- Google Auth、Postgres、Storage、KV 移行経路を本番切替前に検証する。

**移行中の運用ルール:**

| 対象 | ルール |
|---|---|
| 現行 KV 本番 | 変更・デプロイ・データ移行・保存先切替を行わない |
| Supabase 先行版 | 別環境で Auth / Database / Storage / RLS を実装してよい |
| データ | サンプルデータで検証し、本番 KV データは切替承認まで扱わない |
| 認証 | 管理者・スタッフ・顧客とも Google 認証を使う |
| 公開 URL | Supabase 版ではログイン不要の公開カルテ URL を廃止する |
| 顧客権限 | 招待済み飼い主が自分に紐づく犬とカルテだけ閲覧できる |
| 招待 | 店舗発行の 1 回限り QR / URL で Google アカウントと飼い主を紐づける |
| 本番切替 | 別 plan・別承認。先行開発の範囲外 |

**許可範囲:** 本例外は Supabase と Google 認証に限る。他の外部サービス追加を包括的に許可しない。
