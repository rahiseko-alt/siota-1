# AI と共同開発するための環境づくり — 汎用参考資料

> **本書は特定のリポジトリに依存しない汎用資料である。**
> 実案件（非エンジニアの発注者 × 複数の AI）で実際に起きた失敗から抽出した。
> 前提とする状況: 発注者はコードを読まない。AI は「できました」と報告するが、
> その報告自体が信用できない。この非対称を仕組みで埋める。

---

## 1. ルールの正は1つのファイルだけにする

- **人間**: ルールを書く場所を1か所に決める。2か所にあると、AI ごとに言うことが変わる。
- **AI**: 複数の AI（Claude / Codex 等）が触るリポジトリでは、正は `AGENTS.md` 一本。
  `.claude/` `.codex/` `*.claude.json` など**特定の AI だけが読む設定にルールを書かない**。
  `CLAUDE.md` 等は「AGENTS.md に従え」の1行だけにする。`.gitignore` で AI 固有設定の混入を止める。

機械で強制したいことは、特定 AI のフック機構ではなく、
**どの AI でも実行できる1つのコマンド**（例: `npm run check`）に落とす。

## 2. ルールは必ず2行で書く

- **人間**: どのルールも「人間向け1行」「AI向け1行」で書く。読めないルールは、
  発注者が判断できず、認識のすり合わせもできない。
- **AI**: `- **人間**:`（専門語なし）と `- **AI**:`（ファイル名・コマンド・出典はこちらに置く）の2行。

これを守らせるルール自体も2行で書き、ルール一覧の先頭に置く。

## 3. フェーズで区切り、範囲外を機械で止める

大きい作業は「隔離 → 単体で完成 → 結合」のようなフェーズに割り、5つのルールを敷く。

1. **現状あるものだけで完成させる**（新規実装・新規依存の追加禁止）
2. **納品物の完成 ≠ フェーズの完成**
3. フェーズの目的を1行で固定する（例: 現状の整理整頓）
4. 期間中に見つけた問題は**原則あと回し**。例外は「直さないと先に進めないもの」だけで、
   **進める状態までしか直さない**。判断基準は「これを直さないと次へ行けるか？」の1問のみ
5. あと回しは専用の記録に残し、**全フェーズ完了後**に発注者が「直す／放置」を決める

機械化は2本:
- **scope guard**: 現在フェーズ（1行ファイルに `F1` 等）と「触ってよい場所」の表を突き合わせ、
  範囲外への書き込み・`npm install` 等を EXIT 1 で止める。変更ファイル一覧は `git status` から取る
- **gate**: フェーズごとの必須成果物（後述のバッドシナリオ・再発チェック）が**実在するか**だけを見て、
  揃うまで作業場を開けない。「呼んだ記憶」ではなく「成果物の実在」を見るのが要点

## 4. 「調べた」「直した」「解決した」を混同しない

| 層 | やること | やっていないこと |
|---|---|---|
| 調べる（テスト） | 該当するか判定する | 何も直していない |
| 直す（修正） | 症状が出ないようにする | 原因は残っていてよい |
| 解決する | 原因を無くす | — |

**真解決の定義**:

```
問題発見 → 調査（先に「そのエラーを出す検査」を作り、赤を見る）
        → 解決計画 → 解決行動 → 仮解決（真偽未定）
        → ① 解決行動前に戻す   → 最初と同じエラーが出る
        → ② 解決後の状態にする → そのエラーが消える
①②の両方を満たしたときだけ、真解決
```

- ①で**別の**エラーが出たなら、直したのは別のもの。同じ文言のエラーであることまで見る
- 検査は**解決行動の前**に作る。後から作ると「直したものしか捕まえられない検査」ができる
- 機械化: 解決の主張1件につき「赤 / 緑 / 戻して赤」の3出力を記録ファイルに要求し、
  無ければフェーズを閉じさせない。判定の書き換え逃れは **git 履歴の全版**も見て塞ぐ

## 5. 偽解決カタログ（12種）— 見つけ次第この表に足す

| # | 手口 | 潰し方 |
|---|---|---|
| 1 | 赤い検査そのものを消す・弱める | 検査の本数と対象件数を記録し、減ったら EXIT 1 |
| 2 | 調べる場所を減らして「0件」にする | 走査対象の件数を記録し、減ったら EXIT 1 |
| 3 | 例外リストに載せて通す | 例外は「あと回し記録の番号」必須。件数増で EXIT 1 |
| 4 | 合格ラインを下げて通す | 「戻すと赤」の再現出力を必須にする |
| 5 | 関係ない検査の緑で全体が直ったように見せる | 各検査に「何を保証しないか」を書かせる |
| 6 | 報告文だけで直したことにする | 3出力が無ければフェーズを閉じない |
| 7 | 指定を直さず別のものを足して「できた」と言う | 仕様（正とされた見本）との操作集合の差分を機械で取る |
| 8 | あと回し記録に入れて片付いた気になる | 報告に必ずあと回し件数を出す。減っていなければ「解決0件」 |
| 9 | 症状を消す・別の場所へ移す | 削除は復元可能性と呼び出し元の生存確認を必須にする |
| 10 | 壊れるところを一度も見ていない | 3出力を必須にする |
| 11 | 一度の緑で終える | 同一コミットで2回以上同じ結果を示す |
| 12 | 機械の合否を人間の合否と読み替える | 人間の合否は別系統（第9章）で判定する |

## 6. 消去法で正解に近づく（理論的裏づけ）

「欲しい正解は1つ、偽正解は無限。だから偽正解を排除する」——この形は複数分野で確立している:
医療の**除外診断**、心理学の**内的妥当性への脅威**（Campbell & Stanley の固定8項目）、
情報分析の **ACH**（証拠を「支持」でなく「矛盾」で数える）、科学の**強い推論**（Platt）、
ソフトウェア保証の **eliminative argumentation**（defeater を列挙して潰す）、
意思決定の**プレモーテム**（「もう失敗した」と過去形で想像すると原因特定率が約3割上がる）。

各分野に共通する**4つの掟**:

1. **リストは、作業する本人がその場で作らない**（既製・固定のリストを使う）
2. **過去形で書く**（作成時は「もう失敗した。原因は」、実行時は「〜した／こうなっている」の事実確認)
3. **証拠は「支持」ではなく「矛盾」で数える**
4. **全部潰しても「正解」と呼ばない**（暫定。経過観察・残余リスクを持ち続ける）

運用: フェーズ開始前に「バッドシナリオ」を**ちょうど N 個**（例: 10個）出し、発注者の承認を得てから
**実際に実行**して該当の有無を測る。制約は「本質的かつ単純な見落としに限定。
レアケース・影響度の小さい事柄を入れない。1つ外すとフェーズの完了条件が満たせなくなるものだけ。
届かなくても水増ししない」。

## 7. 帳面は3種類

| 帳面 | いつ書くか | 性格 |
|---|---|---|
| **ひな形** | 書かない（固定） | 当てる側。外部既製リスト中心。増えることはあっても減らない |
| **発見帳** | 見つけた瞬間 | 下の分岐で3ファイルに振り分ける |
| **事後記入** | フェーズ完了直前に必ず | ひな形の全行に2択で答える |

発見帳の分岐（航空の安全管理と同じ）:
- **失敗記録** = 起きたと確認できた（事故記録）
- **あと回し** = 起きているが、いまは直さないと決めた
- **経過観察** = 起きたか確かめられていない／潰したが確信が無い（空欄スタート。
  **空のまま終わったフェーズは見落としを疑う**）

当てる時点は**フェーズの境目だけ**（WHO 手術チェックリストが3つの固定停止点で運用される理由と同じ。
常時当てると形骸化する）。照合は**2択・過去形・事実の言葉**
（「良い/悪い」ではなく「見えていた/見えていなかった」。判断語を入れると抜け道になる)。
点数は実行者に付けさせず、監査するとき外から付ける。

## 8. 指標ゲーム（Goodhart の法則）への対策7つ

1. **作業者が操作できない外部基準**を1つ持つ（本書の文脈ではスクリーンショット）
2. **ランダム抜き取り**: どれが検査されるか事前に分からなくする（発注者が気まぐれに1画面選ぶ）
3. **対の指標**: 「検査が緑」の隣に必ず「あと回し件数」「経過観察件数」を並記。
   緑だけ増えて残数が減らないのは不正の兆候
4. **証拠の要求**: 判定ではなく現物（コマンド出力・画像）
5. **再発を重く罰する**: 2度目は新規より重い扱い（再発の9割超は短期間で再発するという実証がある）
6. **大きな書き換えを罰する**: 直しは最小に
7. **目標と測り方を分ける**: 代理指標を目標にしない

## 9. 「人間が使えるか」の判定は別系統にする

- **人間**: 機械の検査が全部緑でも、人間が最後まで進めないことは普通にある。
  人間の合否は**画面の写真だけ**で見る。見るのは2つ——**最後まで行けるか**、
  **間違えても2タッチで戻れるか**。
- **AI**: コードを読んで判定しない（読むと人間に関係ない粗を数え上げる）。
  1タッチごとに全画面スクリーンショットを撮って番号を振るだけの道具を用意し、合否は人間が絵で決める。

ひな形に使う外部既製リスト（比較研究の実証: 併用が単独より効く）:
- **認知的ウォークスルー4問** × 各操作 — 数は少ないが**重い**問題を拾う。
  「次の操作が見えていたか／やりたいことと結びついていたか／進んだと分かったか／戻れたか」
- **ニールセンの10ヒューリスティクス** — 数は多いが軽い問題を広く拾う
- **自分たちの失敗記録の分類**（2階層・頻度順にたたむ。個別事例のままでは使わない。
  再発は雑音ではなく最強の信号）

## 10. 最後に — この仕組み自体の限界

この仕組みは「AI の報告を信用しない」ための構造であって、成果を生む構造ではない。
関所・帳面・定義をどれだけ積んでも、**成果物は1行も進まない**。
仕組みづくりに掛ける時間が成果物に掛ける時間を超えたら、それ自体が偽解決（手口8の変種）である。
仕組みは一度作ったら固定し、以後はフェーズ境目の運用だけにして、残りの時間は全部成果物に使う。
