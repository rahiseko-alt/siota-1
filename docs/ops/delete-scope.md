# 削除は何を消すのか（`docs/deferred.md` #25 の判断材料・2026-08-26）

マスターの問い「**何を削除するのか具体例で言え**」への答え。

サーバ側は**3段階すべて実装済み**で、`npm run verify:delete`（CI・6/6）が
「写真の実体が本当に消えるか」を service_role で数えて毎回確かめている。
**無いのは画面の入口だけ。** 置き場所を決めるために、まず何が消えるかを書く。

犬の名前は seed の X / Y / Z / Q を使う（実在のお客さんは使わない・`A-2`）。

---

## 段階1 — カルテ1件を消す

`deleteReportAssets({ petId, reportId })`（`backend/js/supabase-storage.js:187`）

**例**: 「X くんの **2026-08-15 のカルテ1件**」を消す。

| | 消えるもの |
|---|---|
| DB | `reports` の**その1行**（体重・爪・歯・耳・皮膚・犬体図の印・担当メッセージ） |
| Storage | `{shop_id}/{petId}/{reportId}/` 配下の**写真の実体すべて** |
| 飼い主の画面 | その**1件だけ**が一覧から消える |

**残るもの**: X くん本体、飼い主、X くんの**他のカルテ**（2026-06-05 など）。

順序は「Storage → DB」。逆にすると RLS の条件が崩れ、**写真が誰からも取れない
迷子になる**（`D-20260824-34`・`deferred` #10）。`scripts/guard/delete-order.mjs` が機械で止める。

---

## 段階2 — 犬を1頭消す

`purgePetAssets({ petId })`（同 `:256`）を**犬の行を消す前に**呼ぶ。

**例**: 「**X くん1頭**」を消す。

| | 消えるもの |
|---|---|
| DB | `pets` のその1行と、**X くんのカルテ全件** |
| Storage | X くんの**全カルテの写真すべて** |
| 飼い主の画面 | **X くんが丸ごと消える**（履歴ごと） |

**残るもの**: 飼い主、**同じ飼い主の他の犬**（Y くん・Z くん）とその履歴。

---

## 段階3 — 飼い主を1人消す

`purgeOwnerAssets({ ownerId })`（同 `:271`）を**飼い主の行を消す前に**呼ぶ。

**例**: 「**X・Y・Z を飼っている飼い主1人**」を消す。

| | 消えるもの |
|---|---|
| DB | `owners` のその1行、**その人の犬 3頭全部**、**その3頭のカルテ全件** |
| Storage | 3頭分の**写真すべて** |
| 飼い主の画面 | **ログインしても何も無くなる**（招待リンクも無効になる） |

**残るもの**: 店と他の飼い主だけ。

---

## 置き場所を決めるときに効く違い

| 置く場所 | 押した人が消せるもの | 事故ったときの大きさ |
|---|---|---|
| **⑥顧客カルテの各カルテ** | 段階1（1件） | 小さい。**届いたものを見ながら**消せる |
| **③犬を選ぶ画面の一覧** | 段階1・2 | 中。まとめて整理しやすいが、**隣の子を押し間違える** |
| **④カルテ作成のドック** | 段階1（いま書いているもの） | 小さいが、**下書きの破棄と見分けが付きにくい** |

**どこにも「飼い主を消す」は置いていない。** 段階3 は影響が段違いなので、
画面から押せる場所を作るかどうか自体がマスターの判断になる。

**いま入口が無いこと自体は、飼い主に危害を与えていない。** 消せないだけである。
逆に、置き場所を思いつきで決めると `D-18` 偽-7（言われていない入口を足す）になるので、
このファイルはあくまで**判断材料**であって、提案の採用を促すものではない。
